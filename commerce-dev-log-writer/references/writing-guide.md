# Writing Guide

트러블슈팅, 의사결정, TIL, PR 문서를 작성할 때 공통으로 적용하는 글쓰기 기준이다.

## 1. 지어내지 말고 질문한다

가장 위험한 것은 흔한 사례를 가져와 그럴듯하게 채우는 것이다.

나쁜 예:

```text
N+1 문제로 인해 응답이 느려졌고 fetch join으로 해결했다.
```

작성자가 그렇게 말하지 않았고 코드/로그로 확인하지 않았다면 쓰지 않는다.

좋은 예:

```text
원인은 아직 확정하지 못했다. 다만 CartItem 조회 시 Product 정보가 함께 필요하므로 fetch join 누락 가능성을 의심했다. 실제 원인 확인은 쿼리 로그 확인이 필요하다.
```

## 2. 사실과 해석을 구분한다

- 사실: 실제 에러 메시지, 실패한 테스트명, 응답 코드, 변경한 파일
- 해석: 원인 추정, 설계 판단, 트레이드오프

해석은 다음 표현을 사용한다.

- `~로 보인다`
- `~로 추정된다`
- `확인이 필요하다`

## 3. 실패한 시도를 지우지 않는다

문서의 가치는 성공한 결론보다 과정에 있다.

- 어떤 방법을 먼저 시도했는지
- 왜 실패했는지
- 실패 후 어떤 기준으로 전환했는지

이 내용을 표로 남기면 좋다.

## 4. 프로젝트 언어로 쓴다

8 team 프로젝트에서 이미 쓰는 용어를 사용한다.

- `ApiResponse`
- `AuthMember`
- `AuthMemberResolver`
- `CustomException`
- `ErrorCode`
- `deletedAt`
- `soft delete`
- `cartItemIds`
- `OrderItem 스냅샷`
- `PortOne`
- `Redisson 분산 락`

## 5. 좋은 문장 예시

### 증상

나쁜 예:

```text
주문이 안 됨.
```

좋은 예:

```text
`POST /orders` 요청 시 선택한 장바구니 상품이 존재하는데도 `CART_ITEM_NOT_FOUND` 예외가 발생했다.
```

### 원인

나쁜 예:

```text
Repository가 잘못됐다.
```

좋은 예:

```text
주문 대상 CartItem 조회 조건에 `deletedAt is null`이 포함되어 있어, 이미 주문 처리로 soft delete된 항목은 다시 주문 대상으로 조회되지 않는 것이 정상 동작이었다.
```

### 결정 이유

나쁜 예:

```text
soft delete가 좋아서 선택했다.
```

좋은 예:

```text
CartItem은 `cart_id + product_id` unique 제약을 유지하면서 삭제 이력과 재추가 흐름을 함께 다뤄야 했기 때문에, 물리 삭제보다 `deletedAt` 기반 soft delete를 선택했다.
```

## 6. 부족한 정보 처리

정보가 부족하면 다음 중 하나로 처리한다.

- 질문한다.
- `(작성 필요)`로 남긴다.
- 추정이라면 추정이라고 명시한다.

## 7. 분량 기준

- 트러블슈팅: 한 줄 요약, 문제 상황, 원인, 해결 방법, 배운 점만 있어도 충분하다.
- 의사결정: 선택지 비교와 트레이드오프는 생략하지 않는다.
- TIL: 너무 길게 쓰기보다 오늘의 핵심 배움이 보이게 쓴다.
- PR AI 활용 내역: 짧고 사실 중심으로 쓴다.
