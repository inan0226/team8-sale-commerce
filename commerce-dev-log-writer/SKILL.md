## 역할

8 team Sale Commerce 백엔드 프로젝트에서 발생한 문제 해결 과정, 기술 의사결정, TIL, PR AI 활용 내역, 코드 리뷰 포인트를 팀 컨벤션에 맞게 문서화한다.

이 스킬의 목적은 그럴듯한 문서를 대신 지어내는 것이 아니라, 실제 프로젝트 코드와 작성자가 겪은 과정을 근거로 남기는 것이다.

## 핵심 원칙

- **지어내지 않는다.** 증상, 원인, 시도, 결정 이유, 테스트 결과가 확인되지 않으면 질문하거나 `(작성 필요)`로 둔다.
- **프로젝트 근거를 우선한다.** README, 실제 코드, 테스트, 컨벤션, 에러 로그, 커밋/PR 내용을 우선 확인한다.
- **실제 저장소 구조를 우선한다.** 문서와 코드가 다르면 실제 저장소의 패키지, 클래스명, API 경로를 기준으로 작성한다.
- **팀 컨벤션을 지킨다.** DTO record, `ApiResponse`, `AuthMember`, `CustomException/ErrorCode`, Entity 직접 반환 금지, soft delete 규칙을 반영한다.
- **실패와 트레이드오프를 남긴다.** 실패한 시도, 선택하지 않은 대안, 감수한 단점도 배움으로 기록한다.
- **한국어로 작성한다.** 팀원과 작성자가 바로 제출하거나 PR에 붙일 수 있도록 자연스러운 한국어로 정리한다.

## 작업 전 확인

문서를 바로 쓰지 말고 먼저 아래 정보를 확인한다.

1. 요청이 트러블슈팅, 의사결정, TIL, PR AI 활용 내역, 코드 리뷰 중 무엇인지 분류한다.
2. 프로젝트 맥락이 필요하면 `references/project-context.md`를 읽는다.
3. 코드 스타일이나 PR 반영이 필요하면 `references/code-conventions.md`를 읽는다.
4. Cart/Order 도메인 관련이면 `references/cart-order-checklist.md`를 읽는다.
5. 코드/커밋/로그가 제공되어 있으면 실제 내용을 우선 정리한다.
6. 핵심 정보가 부족하면 필요한 질문을 먼저 하되, 제출 초안이 필요한 상황이면 모르는 항목을 `(작성 필요)`로 남긴다.

## 문서 로딩 규칙

이 섹션의 `references/...` 경로는 이 `SKILL.md`가 있는 스킬 디렉터리 기준으로 해석한다.

- `references/project-context.md`
  - 프로젝트 개요, 기술 스택, 실제 패키지 구조, 주요 도메인 흐름이 필요한 모든 작업에서 읽는다.
- `references/code-conventions.md`
  - 코드 컨벤션, PR 체크리스트, 테스트 네이밍, DTO/API 응답 규칙이 필요한 경우 읽는다.
- `references/cart-order-checklist.md`
  - Cart/Order 구현, 테스트, 리뷰, 트러블슈팅, 의사결정 문서를 작성할 때 읽는다.
- `references/troubleshooting-template.md`
  - 사용자가 "트러블슈팅", "에러 해결", "삽질 기록", "문제 해결 과정"을 요청하면 읽는다.
- `references/decision-record-template.md`
  - 사용자가 "기술 선택 이유", "의사결정", "ADR", "왜 이 방식"을 요청하면 읽는다.
- `references/til-template.md`
  - 사용자가 "TIL", "오늘 배운 것", "구현 과정 정리"를 요청하면 읽는다.
- `references/pr-ai-usage-template.md`
  - 사용자가 "PR AI 활용 내역", "PR 설명", "리뷰어 공유 사항"을 요청하면 읽는다.
- `references/writing-guide.md`
  - 문장 품질, 부족한 정보 처리, 좋은/나쁜 작성 예시가 필요할 때 읽는다.

## 작업 모드

### 1. 트러블슈팅 기록 모드

사용자가 "트러블슈팅 문서 써줘", "에러 해결 과정 정리해줘", "삽질 기록 남겨줘"처럼 요청하면 다음 순서로 작업한다.

1. `references/project-context.md`, `references/code-conventions.md`, 필요한 도메인 체크리스트를 읽는다.
2. `references/troubleshooting-template.md`를 읽는다.
3. 실제 증상, 에러 메시지, 로그, 실패한 테스트, 변경한 코드, 최종 해결 방법을 분리한다.
4. 확인되지 않은 원인은 단정하지 말고 "원인 미상" 또는 "~로 추정"으로 표시한다.
5. 템플릿에 맞춰 문서를 작성한다.
6. 저장 위치는 `docs/troubleshooting/` 아래를 제안한다.

정보 수집 질문:

- 어떤 기능이나 테스트에서 문제가 발생했나요?
- 실제 에러 메시지나 실패한 테스트명은 무엇인가요?
- 원인은 무엇으로 확인됐나요?
- 시도했지만 실패한 방법이 있나요?
- 최종적으로 어떤 코드/설정 변경으로 해결했나요?
- 이 문제를 통해 다음에 조심할 점은 무엇인가요?

### 2. 의사결정 기록 모드

사용자가 "기술 선택 이유 정리해줘", "ADR 작성해줘", "왜 이 방식 선택했는지 남겨줘"처럼 요청하면 다음 순서로 작업한다.

1. `references/decision-record-template.md`를 읽는다.
2. 결정이 필요했던 배경과 제약을 정리한다.
3. 선택지는 최소 2개 이상 비교한다.
4. 최종 선택, 이유, 감수한 트레이드오프를 분리한다.
5. 프로젝트 컨벤션과 연결되는 근거가 있으면 명시한다.
6. 저장 위치는 `docs/decisions/` 아래를 제안한다.

정보 수집 질문:

- 어떤 문제나 요구 때문에 결정이 필요했나요?
- 고려한 선택지는 무엇이었나요?
- 각 선택지의 장점과 단점은 무엇이었나요?
- 최종적으로 무엇을 선택했나요?
- 결정적인 이유는 무엇이었나요?
- 그 선택 때문에 감수한 단점은 무엇인가요?

### 3. TIL / 구현 과정 정리 모드

사용자가 "TIL 정리해줘", "오늘 구현한 거 정리해줘", "장바구니 구현 과정 문서화해줘"처럼 요청하면 다음 순서로 작업한다.

1. `references/til-template.md`를 읽는다.
2. 구현한 기능, 배운 개념, 막힌 부분, 해결 방법, 다음 작업을 구분한다.
3. 단순 나열보다 "왜 그렇게 구현했는지"를 함께 적는다.
4. 저장 위치는 `docs/til/` 또는 개인 학습 기록 위치를 제안한다.

### 4. PR AI 활용 내역 작성 모드

사용자가 "PR AI 활용 내역 작성해줘", "이번 PR 설명 정리해줘"처럼 요청하면 다음 순서로 작업한다.

1. `references/pr-ai-usage-template.md`를 읽는다.
2. AI를 사용한 범위를 과장하지 않고 작성한다.
3. 작성자가 이해한 내용과 직접 검증한 내용을 분리한다.
4. 리뷰어가 봐야 할 공유 사항을 짧게 제안한다.

### 5. 코드 리뷰 체크리스트 모드

사용자가 "코드 리뷰 체크리스트 만들어줘", "PR 전에 확인할 것 정리해줘"처럼 요청하면 다음 순서로 작업한다.

1. `references/code-conventions.md`를 읽는다.
2. 관련 도메인이 Cart/Order면 `references/cart-order-checklist.md`도 읽는다.
3. 빌드, 테스트, 응답 형식, 예외 처리, 권한, 트랜잭션, 동시성, soft delete, 재고 정합성 기준으로 체크리스트를 만든다.
4. 확인하지 못한 항목은 "확인 필요"로 표시한다.

## 문서 저장 규칙

- 트러블슈팅: `docs/troubleshooting/YYYYMMDD-핵심주제.md`
- 의사결정: `docs/decisions/0001-핵심주제.md`
- TIL: `docs/til/YYYYMMDD-핵심주제.md`
- PR AI 활용 내역: PR 본문에 붙여넣을 수 있는 형태로 작성한다.

문서 저장을 실제로 수행하기 전에는 저장할 파일명과 위치를 제안한다.

## 금지사항

- 확인하지 않은 에러 메시지, 원인, 시도, 테스트 통과 여부를 지어내지 않는다.
- 실제 코드와 다른 패키지명, 클래스명, API 경로를 쓰지 않는다.
- Entity를 직접 반환하는 예시를 권장하지 않는다.
- Controller에 비즈니스 로직을 넣는 방향으로 안내하지 않는다.
- `@Data`, 무분별한 `@Setter`, Entity 직접 수정 setter 중심 코드를 권장하지 않는다.
- 인증 회원 ID를 클라이언트 request body나 query parameter로 받는 방식을 권장하지 않는다.
- secret key, DB password, PortOne secret 같은 민감 정보를 문서에 남기지 않는다.
- 팀원 담당 영역이나 공통 설정 변경을 확정적으로 지시하지 않는다. 필요한 경우 공유/리뷰 필요로 표시한다.
